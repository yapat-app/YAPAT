Snippets & Embeddings

Snippets are created as a by-product of embedding generation. A single job cuts each recording into windows, embeds them, and stores the result as a snippet set.

Creating a snippet set

POST /api/datasets/{dataset_id}/embeddings
{
  "embedding_model_id": 1
}

The request can also carry window_size, step_size, and overlap, but a model that requires a fixed value for one of them ignores the request and uses its own. BirdNET, the model registered by the initial migration, requires all three: a 3-second window, a 3-second step, and no overlap. The job is queued on the embeddings queue and processes recordings in chunks of EMBEDDING_CHORD_CHUNK_SIZE (default 25), so that broker overhead follows worker concurrency rather than the number of recordings.

Ready for feeds

A dataset becomes is_ready_for_feed once its default snippet set exists and has status ready. Until then, feed generation is disabled in the interface and embedding-dependent features are unavailable.

Serving snippet data

Endpoint Returns
GET /api/snippets/ Paginated snippets for a dataset and snippet set, with optional recording filter and ID-prefix search.
GET /api/snippets/{id} A single snippet's timing and source metadata.
GET /api/snippets/{id}/audio The extracted window as WAV, with sample-rate and channel headers.
GET /api/snippets/{id}/spectrogram A mel spectrogram rendered as PNG, with configurable mel bands and frequency range.

Extracted audio and rendered spectrograms are cached, so repeated review of the same snippet is cheap.

Deleting a snippet set

Deleting a snippet set removes its snippets and embeddings. If annotations exist against those snippets, the request is rejected unless it explicitly acknowledges the annotation loss, protecting against accidental data loss.
