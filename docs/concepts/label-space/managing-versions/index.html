Managing versions

Label spaces are versioned. A member finalises a label space as a new version, and a team owner decides which version is active. This page describes that lifecycle as the backend implements it.

From conversation to active version

  1. Start a conversation. A label-space session is opened for a team or dataset. It can optionally be seeded with the concepts of the team's current active version.
  2. Build the concept list. Concepts that the user adds from the chat accumulate in the conversation's label space.
  3. Submit. Submitting finalises the label space as a new taxonomy named Version N, with status submitted, attributed to the user who submitted it. The conversation is marked completed and frozen. A submitted version cannot be used for annotation yet.
  4. Promote. A team owner promotes one submitted version to active. The previously active version goes back to submitted and can be promoted again.
  5. Archive. Deleting a custom taxonomy through the API sets its status to archived; the record is kept.

A conversation can also be cancelled, which ends it without creating a taxonomy.

Freeze is a separate, older path. The API also has a freeze endpoint. It finalises a conversation directly into a named taxonomy that is already active, so it skips the review step. Submit and freeze are alternatives, not consecutive steps: each requires a conversation that has not been finalised yet. The web interface offers only the submit action.

Review and promotion

Team owners, and platform administrators, can list a team's versions with GET /api/teams/{team_id}/label-space/submissions. It returns submitted versions by default; the status parameter selects another status or all. A team owner promotes a version with PUT /api/teams/{team_id}/active-label-space, sending the database ID of the custom taxonomy as taxonomy_db_id. Any team member can read the current active version.

What is kept when a label space changes

A change to the label space produces a new version instead of editing the old one, and earlier versions stay in the database with their status. An annotation stores the taxon ID and a snapshot of the resolved name from the time it was made. The annotation record does not point to a label-space version.
