PAM and Annotations

YAPAT cuts long recordings into short segments and stores expert labels against those segments. This page describes that data model.

Passive acoustic monitoring

In passive acoustic monitoring, recorders capture audio over long periods. Experts later annotate what can be heard in it, for example species vocalisations and environmental sounds such as wind or rain. YAPAT does not fix a particular set of labels: in the Annotation Hub, annotators choose from a quick-label list and a GBIF species search, described at the end of this page.

Datasets and recordings

A dataset is the top-level container. YAPAT supports two dataset types:

  • PAM — the default type, for soundscape recordings.
  • FOCAL_RECORDINGS — recordings used with the WSSED species-model workflow.

A dataset's source_uri points at a folder on the mounted data volume. Registering the dataset schedules a background scan that creates one recording entry per audio file. A recording's location is the location value in its metadata. That value is parsed from file names that follow a recognised convention (the site code in SITE_YYYYMMDD_HHMMSS, or the locality in FNJV focal-recording names) and can also be set by importing a recording-metadata CSV on the Datasets page.

Snippets

A snippet is a short window of a recording and is the unit of annotation. Snippets are created when embeddings are generated: the embedding model determines the window length and step. For BirdNET, the model registered by default, the window is 3 seconds with no overlap. Snippets belong to a snippet set, which records the window configuration and the model that produced the embeddings.

Each snippet stores its recording, its start and end time, and its duration. The sample rate belongs to the recording. The API serves the snippet's audio as WAV, with the sample rate in a response header, and the Annotation Hub draws each snippet's spectrogram in the browser from that audio.

Annotations

An annotation links a snippet to a label. Labels given in the Annotation Hub are stored first in the active-learning label store as feedback. They are also written to the annotation table when they resolve to a taxon ID or a species name; a species name is resolved by the taxonomy service, and the resolved name is stored with the annotation.

An annotation stores a namespaced taxon_id, for example gbif:2420576, custom:<id>, wiki:65091, or local:vesperis_iridescentis.

  • A snippet can carry several annotations.
  • The database allows at most one annotation per snippet and taxon ID, regardless of which user created it.
  • The REST API can also create annotations directly, from a taxon_id or a species_name; these are mirrored into the active-learning label store as user labels. The user-study interface does not use this path.

Ground truth and user labels

The active-learning label store keeps a source for each label, either user or ground_truth. Only administrators and team owners can edit ground_truth labels, and those labels are what a cold-start model is trained on. Without ground-truth metadata, the first model is trained from the labels annotators give in bootstrap mode. When a model is retrained, the collected labels serve as its training data.

Where labels come from. In the Annotation Hub, annotators choose from a quick-label list and can search GBIF for further species. The list combines the species of the model checkpoint, the dataset's stored quick labels, the concepts of the team's frozen label space, and species the annotator pinned from GBIF. See What is a Label Space? for how a label space is built.
